為什麼從這裡挑題目

自己想的練習題,面試官看得出來是練習題。池子裡的每一個願望背後都有一個真的人,他寫下自己遇到的問題、希望有什麼。你做出來,是有人真的會用。

  • 需求是別人給的,不是你自己編的 —— 這件事在履歷上差很多。
  • 規格看得到:每個願望都有「還缺幾項規格」,補完就是一份可驗收的需求書。
  • 過程留得下紀錄:認領、進度回報、交出實作,全部公開有時間戳,面試時可以直接翻給對方看。

四步

1
挑一個做得動的 回池邊按「適合新手」,那裡只留規模小或中、而且還沒有人交過實作的願望。點開看「還缺幾項規格」,缺得少的比較好動工。
2
先查市面上有沒有人做過 查大廠內建功能、同類 app、GitHub 既有 repo。查到的多半只是相近,把「對方做到哪、我要補哪一格」寫進認領那句話,這段落差本身就是你的作品說明。真的撞到一模一樣的,把那個連結交上去指路,一樣算幫上忙。
3
補規格缺口,再動手 缺口就是許願者沒講清楚的地方。你可以在願望底下直接問他,也可以自己提個方案請他確認。缺口填平等於規格開好,接下來實作才不會做偏。
4
認領、做、交回 動工前先認領(願望會自動變成「實現中」,讓別人知道有人在做);做到一半也可以回報進度,半成品的紀錄一樣有價值。做完把 repo 連結交上來,誠實寫這個版本做到哪、沒做到哪。

交出去的 repo 要有什麼

  • 真的跑得起來。README 寫清楚怎麼安裝、怎麼跑,別人照著做要能重現。
  • 一張成果截圖。傳到 repo 的 Settings → Social preview,池子這邊會自動顯示成你的實作預覽。
  • 誠實的範圍說明。哪些做了、哪些沒做、已知的問題是什麼。寫出來比藏起來有說服力。
  • 署名。用 GitHub 登入之後交實作會自動掛上已驗證署名,感謝名單上也會有你。

面試時怎麼講這份作品

照這個順序講,對方會聽到你要的東西:

  1. 需求方是誰、他的問題是什麼 —— 證明你做的是真需求,不是練習題。
  2. 規格怎麼來的 —— 你問了哪些問題、補了哪幾項缺口。這一段展示的是溝通與釐清需求的能力,通常比技術細節更稀缺。
  3. 驗收標準是什麼、你怎麼驗的 —— 講得出驗收標準,對方就知道你交付過東西。
  4. 哪裡沒做完、為什麼 —— 講得出取捨,比宣稱全部完美更可信。

先說清楚的幾件事

  • 一個願望可以有多份實作並列,不鎖定、可以多人同時做。已經有人在做的願望,你一樣可以做自己的版本。
  • 「採用哪一版」現階段由站長決定,這是過渡做法。沒被採用的實作一樣公開列在那個願望底下,一樣是你的作品。
  • 這裡不收「幫現有 repo 加功能」,那種請到該 repo 的 GitHub Issues 提。池子收的是還不存在的作品。
  • 做不完可以停,回報一則進度就好。留著紀錄讓別人接得下去,比默默消失有價值。

用 AI 幫你做

整個流程都設計成 AI agent 也能操作:讀願望、補規格、認領、交實作都有公開 API 與 CLI。你可以把整段流程交給 Claude Code 或 Codex 跑,自己負責挑題目、開規格、驗收 —— 那三件事才是面試官想看的。做法見協作指南。
